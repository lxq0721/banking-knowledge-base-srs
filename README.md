# 核心系统迁移知识库 · 需求规格书与测试资产

把存量 COBOL / CICS 资产转成可检索、可追溯、可核验的知识库——这个仓库是它的**需求规格书、测试方案与评测集**，一套从「要做什么」到「怎么验」的完整文档链。

主体按 **GB/T 9385**（计算机软件需求规格说明规范）编写：**144 条**功能与非功能需求、**511 条**验收标准、一套可点开的交互原型，以及每次改版的构建脚本。测试侧另有一套 10 章测试方案与 6 份可直接跑批的评测集。

> 本仓库为**去品牌版本**：不含委托方名称、真实交易码、生产数据与内网信息。文中出现的代码样例均来自公开开源项目（见[评测集语料](#评测集语料)）。

v3.19 与 v3.20 补的都是**链路闭合**，不是新产品能力，分两类：

- **v3.19 三条是「表里写了、条目没接」**：表 6-1 列了「交易（一交易一份）」的产物，功能需求却只到作业说明；FR-STO-21 只限知识版本与应用系统两个维度，没约束链路上的对象该不该进候选集；8.1 只写了「切片 → 知识 → 源码行」的下行溯源，反向取用没有条目。
- **v3.20 三条是「表里没写，实现者各自发挥」**：表 8-5 列了节点与关系，却没有一处规定一条边挂哪一级，于是「§1500 读 AUTHFILE、§1600 写 ACCTFILE」会被一条程序级边抹平；FR-STO-30 写「可达闭包」，而读写边方向是程序→文件，从数据出发一步都走不出去，按字面实现该条直接空转；检索入口只有相似度，问题里明写着对象名也可能命中别处。

这类空白比错误更麻烦：照着条目写用例一条都不会挂，只有真拿一个跨程序的问题去问才暴露。全部历史改动见 [CHANGELOG.md](CHANGELOG.md)（由文档附录 C 自动生成）。**仓库只放最新版成品**，v3.14~v3.19 的中间版本不随仓库发布，需要时从 git 历史取回对应正本，再用 `build/` 下的增量脚本复现。

## 演进主线

项目走到 v3.20，不是线性堆需求，中间有两次转向。看懂这条主线，比逐版读改动要点更快：

| 阶段 | 版本 | 解决的核心问题 |
|---|---|---|
| 规范重构 | v1.5 – v2.0 | Demo 稿互相矛盾、结构松散；v2.0 按 GB/T 9385 重排全文，只动结构不动需求 |
| 定位升级 | v3.0 | 从「演示够用」改为「完整产品」，后续版本从全量里裁剪演示范围，而不是反过来补 |
| 能力补齐 | v3.1 – v3.4 | 按实际接入的资料类型补格式范围；补业务语义与经验累积；补全链路「人工在哪、自动在哪」 |
| 机制细化 | v3.5 – v3.7 | 把「是否调用模型」与「由谁触发」拆开；第 8 章入库建图从 3 张表扩到 6 张；切片口径从「规定切法」退为「参考口径」 |
| **定位转折** | v3.8 | 从「逐条人工审核」改为「辅助检索型」：核验不成立就降级不拦截，人工只守两道门（生成前定范围、上线前抽检） |
| 口径校正 | v3.9 – v3.12 | 可由代码推出的结构从「文档增强」移回「源码必出」；补资料齐备度矩阵；拆开业务术语的两类依据；补来源不一致的判定与疑点清单 |
| **收敛归并** | v3.13 – v3.18 | 按评审意见删冗余、把银行必备而非项目必备的 5 条移出正文；14 组同主题条目并为「一条判据 + 一张表」；v3.16 补回归并过程中漏掉的重算规则，v3.17 补经验沉淀缺的数据对象，v3.18 补资料失效后的知识层处置 |
| **闭合链路** | v3.19 – v3.20 | 反过来查「说了但没兜住」的地方：v3.19 补三处表里写了、条目没接的漏项（交易整链产物、链路检索覆盖、命中代码的知识取用）；v3.20 补三处没写死、靠实现者发挥的取数口径（边的节点粒度、闭包遍历方向、问题里的对象名锚定） |

两次转折值得单独说：

- **v3.8** 把「模型生成的都要人审」这个前提推翻了，改成按下游用途分档。否则 3000 个程序的知识量没有任何团队审得完——人工判定过多是定位错位，不是条目写错。
- **v3.13–v3.18** 反过来的动作是**把已经写进去的东西删掉**。判断标准只有一条：这条需求要改，得同时改几处？改两处的必须合并——历次自相矛盾，全是同一规则写在了文档的两个地方。
- **v3.19–v3.20** 又换了个查法：不看写错没写错，看**写全没写全**。凡是「表里列了、条目没接」或「概念定了、口径没定」的地方，实现者都会自己补一个，补出来的各不相同。

## 编号与优先级约定

- 功能需求 `FR-<域>-两位`，域为 `IMP` 接入 / `PRS` 解析 / `GEN` 生成 / `REV` 核验 / `STO` 入库 / `GRP` 图谱 / `QA` 问答 / `DAT` 数据；非功能为 `NFR-两位`
- 编号与章节号解耦，删条**留空不复用**，新增接域尾
- 优先级只有三档：必须 / 应该 / 可选，**集中在 1.4 与附录 A 维护**，条目内只标注不解释
- AC 的唯一出处是验收清单 xlsx，正文条目只写编号、标题、优先级、约束、描述五段

## 评测集语料

评测集不自己造语料，题目与判分依据全部落在两个公开开源项目的真实代码行上：

| 语料 | 仓库 | 用途 |
|---|---|---|
| CardDemo | [aws-samples/aws-mainframe-modernization-carddemo](https://github.com/aws-samples/aws-mainframe-modernization-carddemo) | 主语料。42 个 COBOL 程序、62 个 copybook、55 个 JCL、21 个 BMS 屏幕、CSD 资源定义与 DDL/DBD |
| Z Open Editor 样例 | [IBM/zopeneditor-sample](https://github.com/IBM/zopeneditor-sample) | 首版语料。COBOL / PL/I / JCL / 混编，适合校验跨语言同名定义 |

100 题分五类：代码与结构事实、业务语义、行员真实提问、来源冲突识别、质量与边界。**判分依据里带文件名与行号**，可逐条回到源码核对。评测集字段、判分规则语法（`A|B|!C|/regex/`）、四步判定顺序见 [`eval-set/README.md`](eval-set/README.md)。

同一套题有三种执行格式，题目与期望要点逐条一致，只是承载方式不同：

| 格式 | 文件 | 用来做什么 |
|---|---|---|
| 正本 | `…实测100题_v2.0.xlsx` | 出题与评审，18 列全量：问题、五类、期望要点、期望出处、机器判定规则 |
| 人工执行版 | `…_基础版_v1.0.xlsx` | 没有跑批环境时逐条手测，去掉机器判定规则，末列留「实际回答」与「判分(0/0.5/1)」 |
| DeepEval 版 | `…_DeepEval版_v1.0.xlsx` | 接框架跑批，列名即 `LLMTestCase` 字段，`actual_output` 与 `retrieval_context` 留空待运行时填 |

跑批链路：

```bash
# xlsx → JSONL（按表头文字取列，不依赖列序）
py -3 build/eval-set/runner/export_jsonl.py --xlsx eval-set/银行知识库评测集_CardDemo实测100题_v2.0.xlsx

# 两种执行格式的 JSONL 由独立脚本导出（列名改过，映射写死在脚本里，缺列直接退出）
py -3 build/eval-set/export_derived.py

# 判分自检（11 条用例，覆盖硬失败、幻觉、标注缺失、规则匹配、待人工）
py -3 build/eval-set/runner/selftest_judge.py

# 对被测接口跑批
py -3 build/eval-set/runner/run_eval.py --input eval-set/jsonl/eval_cd100.jsonl
```

## 改版流程

构建脚本是**增量补丁**，不是从零生成器：每个 `stepN.py` 读取上一版正本、改一处、写出中间文件，链式跑到最后一版。仓库只放最新版成品，所以复现时要先把上一版正本从 git 历史取回来：

```bash
# 取回 v3.18 正本作为起点（提交 58fa1ea 是公开库的初始化提交）
git show 58fa1ea:release/v3.18/核心系统迁移知识库需求规格书_v3.18.docx \
  > release/v3.18/核心系统迁移知识库需求规格书_v3.18.docx

# v3.19：条目 → 表 → 正文/附录 C/版本号 → 修订 → 清单 → 统计
py -3 build/v3.19/step1_items.py
py -3 build/v3.19/step2_tables.py
py -3 build/v3.19/step3_text.py
py -3 build/v3.19/step4_fix.py
py -3 build/v3.19/step5_xlsx.py
py -3 build/v3.19/step6_stats.py
py -3 build/v3.19/v19_check.py      # 一致性校验：条数、逐域对齐、编号区间展开

# v3.20：在 v3.19 正本上再改一轮，step4/step5 专治表 8-5 跨页与列宽
py -3 build/v3.20/step1_items.py
py -3 build/v3.20/step2_tables.py
py -3 build/v3.20/step3_text.py
py -3 build/v3.20/step4_fix.py
py -3 build/v3.20/step5_width.py
py -3 build/v3.20/step6_xlsx.py
py -3 build/v3.20/step7_stats.py
py -3 build/v3.20/v20_check.py      # 23 项校验，含 NFR 两位编号与组尾标题的边界

# 导出 PDF（需本机装有 Word）
py -3 build/tools/export_pdf2.py <docx> <pdf>

# 附录 C 改动后重新生成 CHANGELOG
py -3 build/tools/gen_changelog.py

# 交付前统一文档属性（作者、标题、说明），整个 core.xml 重写
py -3 build/tools/fix_core.py <file> --creator "核心系统迁移知识库项目组" --title "..."
```

改版必查的连带项：表 1-3 与表 A-1 的条数、表 3-2 与表 B-1 的功能组编号（**两表列序不同**）、附录 B 统计、清单统计页。这些位置不随正文自动同步，是历次改版最容易漏的地方——v3.19 的校验脚本首跑就是 71 项失败，全因编号区间没展开（`FR-PRS-01~02、04~05` 要算 4 条）。

## 范围说明

本仓库只覆盖「要不要做、做到什么算成立」，不含技术选型参数（嵌入模型、向量维度、切片长度余量、相似度度量口径）。这些属技术方案，正文仅在需要帮助读者理解需求时保留参考口径，并声明不作为验收依据。

`guide/` 下的测试指南是配套的方法参考，不属于需求正文；两者冲突时以需求书与验收标准清单为准。

## 说明

文档为示例性作品，用于展示需求工程与测试设计的完整链路。涉及的业务口径与合规要求需按委托方实际制度重新确认；`eval-set/` 中的代码事实均可回到对应开源仓库的 commit 校验。
