# 评测集（银行核心系统迁移知识库）

配套 [`../test-plan/核心系统迁移知识库测试方案_v0.8.docx`](../test-plan/) 第 5 章「效果评测」使用的题库。工作簿分两类：前四份**按演进顺序排列，后一份是前一份的替换，不是并列补充**；后两份由 v2.0 派生，题目与之逐条相同，只是执行格式不同（手动执行 / DeepEval 导入）。同目录的 `jsonl/` 与 `results/` 是导出给脚本执行的中间物与跑批留痕。

> 全部题目落在公开样例仓库的真实代码行上，出处写成 `文件:行号`，可逐条回查。不含委托方名称、真实交易码与生产数据。

## 一、六份文件是什么关系

| 文件 | 定位 | 规模 | 结构 |
|---|---|---|---|
| `银行知识库评测集模板_v0.2.xlsx` | **空白模板**，定字段与判定口径，不含真实题目 | 8 页；字段 17 列；示例题 12 条 | 填写说明 / 评测集 / 分类配比 / 字段规范 / 示例题 / 集合元信息 / 执行记录 / 脚本接口 |
| `银行知识库评测集_分视角题型示例_v1.0.xlsx` | **出题方法的样本**，按「谁在问」拆视角，用来对齐口吻与判分口径 | 9 页；68 条 | 每视角一页 + 代码里没有的 22 个方向 + 同一事实三种问法 + 判分口径 |
| `银行知识库评测集_ZOpenEditor实测100题_v1.0.xlsx` | **第一版实测 100 题**，素材为 Zowe COBOL 示例集 | 8 页；100 条；17 列 | 与模板同构 |
| `银行知识库评测集_CardDemo实测100题_v2.0.xlsx` | **当前正本**，素材换为信用卡核心系统样例 | 单页；100 条；18 列 | 五分类分区，组间空一行；表头 4 行，冻结 `D5` |
| `银行知识库评测集_基础版_v1.0.xlsx` | 由 v2.0 派生，**人工逐条执行**用 | 单页；100 条；14 列 | 判分所需的期望要点、期望出处、来源级别、内容状态、有无答案、是否需角色保留，机器判定规则与 `checks` 去掉，末尾留空列「实际回答」 |
| `银行知识库评测集_DeepEval版_v1.0.xlsx` | 由 v2.0 派生，**导入 DeepEval 跑批**用 | 单页；100 条；14 列 | 表头改为框架字段：`input` / `expected_output` / `actual_output`（运行时填）/ `retrieval_context`（运行时填），判分侧字段保留在后几列 |

后两份的取舍：手动执行不需要机器判定规则，留着只会让人以为要跑脚本；DeepEval 认的是固定字段名，用中文列名导不进去。**两份的题目、期望要点、期望出处与 v2.0 逐条一致**（编号同为 `EV-CD-001` 起），所以换格式不改变评测口径，跑出来的数可以直接对比。

演进原因：ZOpenEditor 只有客户文件与交易文件两个示例，缺交易码清单、屏幕定义、码表与业务文档，**行员视角的题一条也写不出来**。v2.0 换成 CardDemo 后补上 21 个 BMS 3270 屏幕、18 组 CICS 资源定义、7 张码表，行员题从 0 条变成 24 条。ZOpenEditor 那份保留，因为它有 PL/I、HLASM、REXX 三种语言，CardDemo 完全没有。

分视角示例（v1.0）是方法样本，不是题量补充：它解决的是「题目角度单一」的问题——第一版 100 题里开发视角 78 条、行员 0 条，因为出题时按代码结构铺开，没有从「谁在什么场景下会问」反推。

## 三、题目类型与配比

`type_no` 沿用模板九类：1 精准命中 / 2 同义改写与跨语言 / 3 信息分散（多跳） / 4 知识库不存在（幻觉） / 5 冲突信息 / 6 异常与边界 / 7 跨模态 / 8 多轮对话 / 9 元数据过滤。

v2.0 实际配比：

| 类型 | 条数 | | 类型 | 条数 |
|---|---|---|---|---|
| 1 精准命中 | 32 | | 5 冲突信息 | 13 |
| 2 同义改写+跨语言 | 9 | | 6 异常与边界 | 9 |
| 3 多跳 | 29 | | 7 跨模态 | **0** |
| 4 无答案（幻觉） | 6 | | 8 多轮对话 | 2 |

难度：简单 26 / 中等 44 / 困难 30。第 7 类整类为 0 是允许的裁剪（CardDemo 只有架构图 PNG，没有界面图像），不是遗漏；无答案题另占 10%（10 条，含类型 4 与其他类里要求「应明确拒答」的条目），达到 10% 硬下限。

**冲突题里故意混了「看似冲突、实为并列」的 3 条**（README 24 个交易 vs CSD 18 个、BMS 商户名 30 字 vs 存储 `X(50)`、PL/I `CHAR(80)` vs COBOL 387 字节）。判据是「同一对象同一属性取值能否同时成立」，这三条能同时成立，答成冲突即说明判据没真正用上。

## 四、判定口径

完整规则见 [`../build/eval-set/runner/README.md`](../build/eval-set/runner/README.md)，三条要点：

- 机器判定规则写作 `A|B|!C|/regex/`：`|` 分隔，`!` 是否决项，`/…/` 是正则，留空表示只能人工判。
- 判定顺序不可颠倒：硬失败（5xx / 超时 / 空响应）→ 无答案题专项（查幻觉）→ 级别标注缺失 → 规则匹配 → 无规则即待人工。
- `must_not` **不进命中率分母**，`total = len(must) + len(regexes)`。

不会说「我拒绝」的回答才是好的拒绝类回答，所以空输入、越权索取密码、指令注入这三类只能人工判（v2.0 里共 3 条）。

## 五、怎么跑

```bash
# 1) 导出（按表头文字取列，分组标题行与统计块会被自动跳过）
python build/eval-set/runner/export_jsonl.py eval-set/银行知识库评测集_CardDemo实测100题_v2.0.xlsx \
       --hdr-row 4 --first-row 5 -o eval-set/jsonl/eval_cd100.jsonl

# 2) 先自检判定逻辑，排除规则本身写错
python build/eval-set/runner/selftest_judge.py

# 3) 干跑（桩接口，只验链路通不通）
python build/eval-set/runner/run_eval.py --input eval-set/jsonl/eval_cd100.jsonl \
       --out eval-set/results/results_cd100.csv
```

接真实问答接口时改 `run_eval.py` 里的 `http_call` 一处即可。

基础版与 DeepEval 版不走 `export_jsonl.py`——那脚本按 v2.0 的 18 列表头取字段，而这两份为人工阅读改过列名，喂进去会报「表头缺字段」。用同目录下专为它们写的脚本：

```bash
# 同时重出两份 jsonl，并从两边交叉核对编号
py build/eval-set/export_derived.py
```

它只做三处变换：期望要点在表里是「一行一条」，基础版补 `1）2）` 序号、DeepEval 版用「；」连成一段（`expected_output` 容不下列表）；期望出处按行拆成列表；「是否需角色」转布尔、「自研判据」的 `must:X | !Y | /re/` 解析成 `{must, must_not, regex}`，一条判据都定不出来的判 `manual`（本集 3 条）。改列名时要同步改脚本里的 `BASIC_MAP` / `DEEPEVAL_MAP`，脚本会对缺列直接报错退出，不会静默导出一批空字段。

DeepEval 版不进 `run_eval.py`：把 `eval_deepeval.jsonl` 逐行读成 `LLMTestCase`，`actual_output` 由被测接口填、`retrieval_context` 由检索侧填，再按框架的指标算分。

## 六、`jsonl/` 与 `results/` 里是什么

| 文件 | 说明 |
|---|---|
| `eval_cd100.jsonl` | v2.0 的 100 条导出，脚本直接读 |
| `eval_basic.jsonl` | 基础版的 100 条导出，只有人工判分需要的字段 |
| `eval_deepeval.jsonl` | DeepEval 版的 100 条导出，字段名即框架字段，`actual_output` / `retrieval_context` 留空待运行时填 |
| `eval_zowe100.jsonl` | v1.0 的 100 条导出（含已修正的 EV-CBL-058） |
| `views_eval.jsonl` | 分视角示例的 68 条导出 |
| `eval_set.jsonl` | 模板配套的示例导出，用于验证链路，不是题目 |
| `results_cd100.csv` / `results_zowe100.csv` / `results_sample.csv` | 干跑留痕 |

**`results/` 下的三份结果都是桩数据，不能当质量结论。** 桩按规则拼字符串作答，通过率只说明判定链路能跑通，不说明知识库好坏。要得真实结论，须接真实接口重跑。

## 七、已知局限

1. **判定规则偏严**。有的条目要求答出英文对象名，答中文译名会判不过。首轮真实跑批后建议抽 20 条校准再据实调整。
2. **行员题的规则只验硬事实**。「17 字节」「9(7)V99」这类能自动判，但「有没有答到业务后果」机器判不出来，必须机判粗筛 + 人工复核后半段。
3. **18 列在 A3 上没法既压一页宽又字大**。实测 50% 缩放为 18 页 4.6pt、70% 为 28 页 6.4pt，且任何比例下都横向分 2 页。现按 `fitToWidth=1` 处理（8 页，便于整体翻阅）；打印看清字需在 Excel 里自行调缩放。
4. **样本库不是银行核心系统**。CardDemo 是信用卡演示应用，冲正码在码表里有、实现为空，权限字段存在、判断缺失。凡落到「代码里没有的方向」（见分视角示例第 06 页 22 条）的题，应标「库内不存在」进幻觉专项，不能标「是」再要求模型硬答。
